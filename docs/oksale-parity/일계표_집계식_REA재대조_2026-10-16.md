# 일계표 집계식 — REA 재대조 (2026-10-16, 일론머스크2)

## 1. 이전 «호출자 추적 실패»가 풀린 경위 (Evidence)
- 보조함수 `0x78c6b0`(DailyBalanceTable 한 줄 삽입)을 «직접 call 0건»으로 못 찾았던 이유: VB 폼의 **메서드 표(vtable)를 통한 간접 호출**(`call dword ptr [reg+0x6fc]`)이다.
  - Ghidra xrefs(`docs/analysis_rea/oksale/ghidra/xrefs.jsonl`): `0x419b8a → 0x78c6b0` 한 건. 그 자리 `0x419b82`는 thunk(`sub dword [esp+4],0xffff ; jmp 0x78c6b0`), 가리키는 표 `0x4193a8`(폼 메서드 포인터 열), 표 주소는 `0x419134`가 가짐.
  - 집계 함수 `0x790fb0`(26,902바이트, frmDailyBalance 안)에 `call [reg+0x6fc]` 6곳이 삽입 호출이다.
- 도구: `docs/analysis_rea/oksale/tools/disasm.py`(capstone·pefile), 이번 추가 스크립트는 세션 임시 폴더(trace.py: 문자열·VB 런타임 호출을 순서대로 추출).

## 2. 의사코드 (Pseudo code)
조회 SQL(0x790fb0, 문자열 근거): `select * from SlipHeader Where SlipDate Between '<월 1일 추정>' And '<조회 종료일>' And CustomerName Between '<시작>' and '<끝>' and (SlipKind = '1' or '4' or '2' or '3' or '0' or '9' or 'A' or 'B') Order by CustomerID`
- 같은 달 제한: «시작일자와 마지막 일자가 같은 달이어야 합니다.»(0x790410 검증 문자열).
- 한 줄(전표)씩 읽으며 거래처(CustomerID)가 바뀔 때마다 DailyBalanceTable에 한 줄 삽입(`insert into DailyBalanceTable values (Kind, CustomerName, 판매/구매금액, 반품금액, 수금/지급금액)`). **세 값이 모두 0이면 삽입하지 않는다**(`fcomp 0` 3회).
- 두 묶음으로 나눈다(전표종류 비교 문자열):
  - **매출 쪽 {1, 3, 9, A}**: 거래처 줄 Kind='5', 소계 «매출계»(Kind 6)·«월매출계»(Kind 7).
  - **매입 쪽 {2, 4, 0, B}**: 거래처 줄 Kind='1', 소계 «매입계»(Kind 2)·«월매입계»(Kind 3), 구분줄 Kind 4.
- 전표 종류별 누적(거래처 단위 `금액=amt, 반품=ret, 수금지급=rcp`; 합계 = Amount + Tax − Discount):

| 종류 | 의미(실측 패턴) | amt | ret | rcp |
|---|---|---|---|---|
| 1 | 매출 | += 합계 | | += Receipt |
| 3 | 매출 반품 | | += 합계 | −= Payment |
| 9 | 수금 전표 | −= Discount | | += Receipt |
| A | 구형 매출 | += Amount | | |
| 2 | 매입 | += 합계 | | += Payment |
| 4 | 매입 반품 | | += 합계 | −= Receipt |
| 0 | 지급 전표 | −= Discount | | += Payment |
| B | 구형 매입 | += Amount | | |

- **일 구간** = 조회 시작~종료일의 전표 → 거래처 줄 + «매출계/매입계»(일 합계 amt·ret·rcp). **월 구간** = 일 구간 합계에 **조회 시작일 이전(같은 달) 전표**(`SlipDate < 시작일`)를 같은 식으로 더한 값 → «월매출계/월매입계» (월 1일~조회 종료일 누계).
- 읽기(0x78e850): `select * from DailyBalanceTable Order by Kind , SalesBuyingAmount Desc`.

## 3. 대조 (실측)
- **원본이 남긴 출력**: `오케이세일/Report5/Print.mdb`(2010-02-22 수정)의 DailyBalanceTable 6행 — Kind 2·3(매입계 0, 월매입계 5,184,341.5)·4·5(세이브에너지 173,280)·6(매출계 173,280)·7(월매출계 17,982,400). Kind 값 구조(2~7)와 매출 거래처 줄 Kind=5는 이 출력과 일치. 매입 거래처 줄 Kind=1은 표본에 매입 거래처가 없어 번호 순서(1→매입계 2→월매입계 3→구분 4→매출 5→6→7)와 어셈블리 문자열 '2'·'3'·'4'·'5'·'6'·'7' 배치로 «추정»한 값이다.
- 전표 대조: 같은 거래처(800415 세이브에너지)의 2010-02-22 SlipKind=1 전표 173,280원이 `Data/S10.mdb`에 실존(금액 일치).
- **월계 숫자는 불일치(Unknown)**: S10.mdb의 2010-02-01~22 종류1 합계 = 18,648,608 ≠ 출력의 17,982,400, 종류2 합계 = 12,057,634.5 ≠ 5,184,341.5(소수 .5 자리는 일치). 어떤 날짜 구간 조합으로도 이 값이 안 나와, 출력 이후 전표가 추가·수정·삭제된 것으로 «추정»(미확인). 그러므로 **월계 범위 규칙(월 1일~종료일)은 어셈블리 근거이고 원본 출력으로 숫자 검증은 못 했다.**

## 4. 구현 반영

## 5. Unknowns
1. 월계 숫자의 원본 출력 대조 불가(위 불일치, 전표가 이후 바뀐 것으로 «추정»).
2. (해소) 조회 SQL의 시작일은 «월 1일»이다: SQL의 첫 인자를 만드는 함수 `0x675570`이 `Format(날짜,"YYYY-MM") & "01"`을 `DateValue`로 바꿔 돌려준다(문자열 `'YYYY-MM-DD'`·`'01'`, `__vbaVarCat`·`__vbaDateVar` 확인). 따라서 월계 = 월 1일~조회 종료일.
3. 한글 캡션 «거래처명을 입력하세요.»·CustomerName Between 범위 입력 화면(전 거래처 기본값)은 이번에 대조하지 않았다.
