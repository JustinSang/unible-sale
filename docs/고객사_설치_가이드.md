# 고객사 설치 가이드 (A안: 고객사마다 따로 설치) — 2026-10-16

**원칙**: 코드는 하나(이 저장소), 고객사마다 **자기 Vercel 프로젝트 + 자기 Supabase 프로젝트 + 자기 환경변수**. 회사 사이에 데이터가 섞일 길이 없다. 동산화스너는 환경변수를 비워 둔 지금 그대로 쓴다(코드 기본값이 동산화스너 — 이 문서의 어떤 단계도 동산화스너 배포를 바꾸지 않는다).

> 상태 표기: **확인됨** = 이 저장소에서 실제로 시험함 / **미확인** = 문서대로 하면 될 것으로 추정하나 아직 실제 고객사 설치로 시험하지 못함. 아직 한 번도 실제 고객사 설치를 해 본 적이 없다 — **첫 고객사 설치는 이 절차의 첫 시험**이니 «미확인»을 하나씩 확인하며 이 문서를 고친다.

## 0. 준비물 (고객사마다)
- Supabase 프로젝트 1개(무료 한도 확인 — 10-16 기준 동산화스너 프로젝트는 존재하지 않아 재생성 필요), Vercel 프로젝트 1개(같은 GitHub 저장소를 연결), 고객사 회사 정보(상호·사업자번호·대표·주소·전화·팩스·업태·종목), 도장 그림(PNG, 흰 배경 가능 — PDF 때 흰색을 투명 처리), 로그인 사용자 목록, 초기 자료 엑셀(품목·거래처).
- 팝빌(팩스)·Resend(이메일) 키는 **고객사 명의로** 따로 받는다(미확인: 계정 구조는 팝빌/Resend 약관 확인 필요 — 같은 키를 고객사끼리 공유하면 안 된다).

## 1. DB 만들기 (Supabase)
1. 새 프로젝트 생성 → SQL Editor에서 `scripts/supabase_schema.sql` 실행(멱등, **확인됨**: 열 목록이 앱 데이터와 일치).
2. **RLS는 4단계(키 설정·배포) 뒤에** `scripts/supabase_rls.sql` 실행.
3. Project Settings → API 에서 URL, anon 키, **service_role 키**를 복사해 둔다(service_role 키는 채팅·이메일·git에 쓰지 말 것).

## 2. 표지(브랜드) 환경변수 — `.env.example` 아래쪽 참고
| 변수 | custom 고객사 예 | 비워 두면 |
|---|---|---|
| `NEXT_PUBLIC_TENANT` | `custom` | 동산화스너 |
| `NEXT_PUBLIC_COMPANY_NAME` | `○○상사` | (custom인데 비우면 «고객사») |
| `NEXT_PUBLIC_COMPANY_DEPT` / `_TAGLINE` / `_ITEMS` | 선택 | 빈 문구 |
| `NEXT_PUBLIC_SEAL_PATH` | `/seal-acme.png` (`public/`에 넣은 파일) | 도장 없이 인쇄 |

`NEXT_PUBLIC_*`는 **빌드할 때** 박히므로 바꾸면 다시 빌드·배포한다. 회사 상세 정보(사업자번호·대표·주소·전화)는 코드가 아니라 설치 뒤 **환경설정 화면에서 입력**해 DB에 저장한다(확인됨: 인쇄 양식이 DB의 회사 정보를 쓴다. 단 custom 고객사 화면을 실제로 띄워 본 시험은 §6 참고).

## 3. 서버 환경변수 (Vercel → Settings → Environment Variables)
`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`(서버 전용, `NEXT_PUBLIC_` 금지), `AUTH_SECRET`, `AUTH_USERS`(로그인, `scripts/make_auth_user.mjs`), 필요하면 `POPBILL_*`·`RESEND_API_KEY`. **로그인(`AUTH_*`)은 처음부터 켠다** — 고객사 데이터를 인터넷에 두는 서비스다.

## 4. 배포
- Vercel 프로젝트 Build Command: `npm run build:tenant`(고객사 배포에서 동산화스너 도장·화면 캡처 파일을 빌드 결과에서 제거 — `scripts/prepare_tenant.mjs`, 동산화스너 배포는 기존 `next build` 그대로).
- 배포 후 로그인 → 화면 확인 → **그 다음** `scripts/supabase_rls.sql` 실행 → 화면이 여전히 보이는지 확인(순서를 어기면 «데이터 없음»). 미확인: 실제 Vercel에서의 첫 배포.

## 5. 초기 자료 넣기
1. 환경설정에서 회사 정보 입력, 도장 이미지는 `public/`에 넣고 `NEXT_PUBLIC_SEAL_PATH`로 지정(재빌드).
2. 거래처관리 «📥 엑셀로 거래처 가져오기», 품목관리 «📥 엑셀로 단가 수정» → «새 품목 N건 등록»(확인됨: 둘 다 미리보기 후 반영, 기존 값은 덮어쓰지 않음). 헤더 이름은 코드 안 별칭 표(거래처명/상호, 사업자번호, 대표자, 전화, 품명, 규격, 단위, 판매단가, 매입단가 …).
3. 거래처별 초기이월금은 거래처 양식에서 입력(기준일은 전 거래처 공통 — 한 번에 같이 입력).

## 6. 설치 뒤 점검표 (고객사마다 한다)
- [ ] 로그인 화면 제목·헤더·거래명세표에 **다른 회사 이름이 없다** (`/login`, 첫 화면, 거래명세표 인쇄 미리보기, 영수증)
- [ ] 로그인 없이 `/api/products`가 401, 직원 계정으로 삭제가 403 — `bash scripts/test_auth_http.sh`
- [ ] 변경 이력 탭에 저장·삭제가 남는다
- [ ] 시험 전표 1건 저장 → PDF 저장 → 삭제
- [ ] RLS 켠 뒤에도 목록이 보인다 / anon 키로 직접 조회하면 비어 있거나 거부된다
- [ ] 백업: Supabase 자동 백업 범위(요금제별로 다름) 확인
- [ ] 팩스·이메일은 고객사 키로 시험 발송 1건(대표 승인 후)

## 7. 업데이트 방식
한 저장소의 같은 커밋을 고객사 Vercel 프로젝트들이 각자 빌드한다. 스키마가 바뀌면 `scripts/supabase_schema.sql`(멱등)을 **각 고객사 DB에 다시 실행**해야 한다 — 고객사가 늘면 이 부분이 운영 부담이다(그때가 B안: 한 서비스·여러 회사로 갈 시점).

## 8. 이번 단계에서 하지 않은 것(정직)
- 한 번도 실제 고객사 배포를 해 보지 못했다. 이 가이드의 시험은 «환경변수만 바꿔 같은 코드로 빌드해 화면 문구가 바뀌는지» 수준이다(§검증 결과).
- 양식(거래명세표 등)의 모양은 동산화스너가 쓰던 오케이세일 원본을 복원한 것 하나뿐이다. 다른 업종은 양식 요구가 다를 수 있다(고객사별 양식 변형은 미구현).
- 가격·계약·고객사 데이터 소유/삭제 정책, 법률 검토는 대표님·법률단 몫.

## 10. 동산화스너 보호 원칙
동산화스너 배포의 환경변수는 건드리지 않는다(`NEXT_PUBLIC_TENANT` 비움 = 동산화스너). 고객사 작업은 **고객사 전용 Vercel 프로젝트·전용 환경변수**에서만 한다. 코드 변경은 같은 저장소라 동산화스너에도 반영되므로, 코드 푸시 전 위 «동산화스너 빌드» 시험(제목·헤더·도장·회사정보)을 먼저 한다.
