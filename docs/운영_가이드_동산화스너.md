## 5. 로그인 켜기 (인터넷 접속·여러 사람이 쓰기 전에)
**브라우저 화면에서 켠다(권장)**: 이 컴퓨터에서 `localhost:3300`을 열고 «환경설정 / 동기화» 탭 → «로그인·사용자 설정»에서 관리자(admin)와 직원(staff)의 아이디·이름·비밀번호를 입력 → «저장하고 로그인 켜기». 저장하면 웹(3300)이 스스로 다시 시작되고 로그인 화면으로 넘어간다. 켠 뒤에는 관리자만 이 화면에서 사용자 추가·역할 변경·비밀번호 변경(칸을 비우면 그대로)·«로그인 끄기»를 할 수 있다. 로그인이 꺼진 동안의 **최초 설정은 이 컴퓨터(주소창이 localhost)에서만** 된다(같은 와이파이·Tailscale의 다른 기기에서는 막힘). 한계: 이 판정은 요청 머리글(Host·x-forwarded-for)로 하므로, 같은 네트워크의 누군가가 두 머리글을 일부러 속여 보내면 막지 못한다 — 켜기 직전에 바로 이어서 설정할 것.
**터미널로도 가능**(터미널에서 직접 — 비밀번호는 화면에 안 보이고 파일에는 해시만 저장된다):
```
bash scripts/server/enable_login.sh        # 아이디·이름·역할(admin/staff)·비밀번호를 한 명씩 입력, 관리자 한 명 이상 필수 → 웹(3300)만 자동 재시작
bash scripts/server/enable_login.sh --off  # 끄기(app.env에서 로그인 두 줄만 빼고 웹 재시작, 복사본 남김)
```
스크립트가 `data/live/app.env`(git 안 올라감, 권한 600)에 `AUTH_SECRET`·`AUTH_USERS`를 쓰고, 쓰기 전 `app.env.bak_날짜`로 복사해 둔다.
**수동으로 쓸 때의 함정**: `app.env`는 셸이 읽는 파일이라 값을 **작은따옴표로 감싸야** 한다(`AUTH_USERS='[{"id":…,"hash":"scrypt$…"}]'`). 따옴표 없이 쓰면 `$`·`"` 때문에 읽다가 깨진다(예전 문서의 예시가 따옴표가 없어 틀렸다).
꺼 둔 상태(파일 없음)에서는 **접속할 수 있는 누구나 모든 기능을 쓴다.** 웹 서버(3300)는 이 컴퓨터만이 아니라 같은 와이파이·Tailscale에서도 열려 있다.
- 역할: admin은 전부, staff는 삭제·미동 전환·설정 변경·변경 이력 조회가 막힌다. 로그인 쿠키는 14일. 비밀번호를 잊으면 스크립트를 다시 실행해 전체 사용자를 다시 입력한다.
- 시험(2026-10-17, 시험용 폴더·복사본 DB·무작위 시험 비밀번호): 로그인 없이 `/`→307·API→401, 틀린 비번·없는 아이디 401, admin·staff 로그인 200, staff 삭제·변경이력 403·admin 통과, 위조 머리글·위조 쿠키 401.

## 5-1. 거래처 잔액(전잔액) 맞추기 — 꼭 해야 하는 한 번의 작업
이관된 옛 전표 때문에 «전표만의 누계»는 실제 잔액과 다르다(예: 만주배관센터 789만원). 그래서 **실제 거래처별 잔액표(엑셀)와 기준일**이 필요하다.
1. 거래처관리 «📥 엑셀로 거래처 가져오기» → 엑셀(거래처명·사업자번호·초기이월금) 읽기 → «전 거래처 기준일 적용» 켜고 기준일 입력 → 반영. 받을 금액은 +, 줄 금액은 −.
2. 반영하면 모든 거래처의 미수금이 장부 잔액으로 자동 재계산된다(`POST /api/recalc-receivables`, `{"dryRun":true}`로 미리 볼 수 있음).
3. 이후 전표 저장·삭제·수금 때마다 거래처 미수금이 장부 잔액과 같게 유지되고, 거래명세표의 «전잔액»도 그 값이다.
기준일을 넣기 전에는 예전 방식(전표 저장 때 미수 더하기, 수금 때 빼기)으로 동작하며 전잔액은 «사용 시작 이후 금액»만 반영한다.

## 6. 망가졌을 때 (복원)
1. 웹·DB 중지: `launchctl bootout gui/$(id -u)/com.unible.sale.web ; launchctl bootout gui/$(id -u)/com.unible.sale.localdb`
2. 현재 파일을 옮겨 두기: `mv data/live/unible_live.sqlite* data/live/망가진_$(date +%H%M)/` (지우지 말고 보관)
3. 백업 중 원하는 시점 선택(로컬 `data/live/backups/` 또는 드라이브 `live_db_backups`) → `cp 백업파일 data/live/unible_live.sqlite`
4. 다시 시작: `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.unible.sale.localdb.plist` 후 web도 같은 방식.
복원하면 «백업 시점 이후»에 입력한 전표는 사라진다 — 그래서 백업이 잦고 변경 이력(`audit_log`)이 남는다.

## 7. 알려진 한계 (정직)
- **한 대 컴퓨터의 파일**이다. 이 컴퓨터가 고장 나면 마지막 백업(최대 하루 전, 드라이브 업로드 기준)까지만 복구된다. 중요한 입력이 많은 날은 `bash scripts/server/backup_to_drive.sh`를 퇴근 전에 한 번 더.
- 동시 사용자는 소수(쓰기 직렬 처리). 직원 여러 명이 동시에 많이 입력하는 규모면 Supabase(또는 PostgreSQL)로 옮겨야 한다.
- RLS·권한 정책 같은 DB 수준 보안은 없다. 대신 이 DB는 **127.0.0.1에서만** 받고, 접근은 웹 서버(로그인 보호 가능)를 거친다.
- 이전: 운영 Supabase가 생기면 `python3 scripts/server/local_db.py --export out.json`으로 내보내 `scripts/migrate_to_supabase.ts`로 올린다(내보내기 형식은 `{db, prices}` — 이전 스크립트에 맞춰 쓰는 연결은 **아직 안 만들었다**).
